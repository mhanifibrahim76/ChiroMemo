# Database

Provider: **Supabase Postgres** · Access layer: **Supabase Data API + RLS**
· Migrations: `supabase/migrations` (native Supabase location) — the source of
truth for the database
· Generated Supabase types: `src/lib/supabase/database.types.ts`, used as the
`Database` generic on the server client.

> Prisma was the data-access layer during Phase 2 and has been **removed**. There
> is no ORM, no schema file, and no direct Postgres connection in the application
> anymore.

> Status: **APPLIED and VERIFIED (2026-10-02, updated 2026-10-07).** The initial
> migration has been executed against the Supabase project and the resulting schema
> was inspected read-only with a catalog query pass (Q1-Q18, all PASS). Phase 1A
> schema changes were applied on 2026-10-07. The `public` schema now holds 10
> tables, 4 enums, 15 foreign keys, RLS on all 10 tables and 36 policies. `users`
> held 1 row at verification; all other tables were empty.

## Native conventions (authoritative)

The database is owned by the SQL in `supabase/migrations`, which is the single
source of truth. Everything below describes the **real database**:

- snake_case table, column, constraint, index and policy names.
- `timestamptz` for every timestamp.
- `public.users.id` is a `uuid` and mirrors `auth.users.id` **by convention**.
  There is no foreign key to `auth.users`, and no sync trigger.
- All other ids are `text` holding a cuid generated by the application.
- `updated_at` has `DEFAULT now()` only; there is **no update trigger yet**.
  Automatic bumping is a separate task.
- Ownership is enforced by **Row Level Security**, not only by application code.

## Connecting to Supabase

The application connects **only** through the Supabase Data API using the
typed client in `src/lib/supabase/server.ts`. There is no direct Postgres
connection string in the code, and `DATABASE_URL` is no longer read or
validated.

```ts
import { createClient } from "@/lib/supabase/server";
import type { Database } from "@/lib/supabase/database.types";

const supabase = await createClient();
// createServerClient<Database>(url, anonKey, ...) -> supabase.from("users")
```

Because the client is built from the user's session, every request is made with
the `authenticated` role, so RLS applies to all application queries. Do not
introduce a service-role client to work around a policy; fix the query.

No pooler or port configuration is needed in the application. Port 6543 (the
transaction pooler) remains relevant only if a future admin script needs a direct
connection, and `DATABASE_URL` would then be supplied out-of-band, not committed.

Privileges after the migration:

- `anon` — **no** table privileges in `public` (the migration's `REVOKE`).
- `authenticated` — `SELECT`, `INSERT`, `UPDATE`, `DELETE` on the 8 tables,
  narrowed per row by RLS.
- `service_role` — retains its Supabase-managed privileges and bypasses RLS.

Data types confirmed: `public.users.id` is `uuid` with **no default** (the value
is supplied from `auth.users.id` by application convention), all six `user_id`
columns are `uuid`, every other id is `text` (cuid from the application), all
timestamps are `timestamptz`, and `learning_activities` has no `updated_at`.

## Generated Supabase types

`src/lib/supabase/database.types.ts` was generated from the **live** `public`
schema with the Supabase CLI (not hand-written):

```bash
npx supabase gen types typescript --project-id <project-ref> --schema public > src/lib/supabase/database.types.ts
```

That command is read-only — it introspects the schema and writes no data. It
requires an authenticated CLI session (`supabase login`).

- Exports `Json`, `Database`, `Tables`, `TablesInsert`, `TablesUpdate`, `Enums`,
  `CompositeTypes`, `Constants`.
- Covers the 8 tables and 4 enums, with generated `Relationships` blocks.
- Encoding: **UTF-8 without BOM**, matching every other `.ts` file in `src/`.
  (The CLI output was originally captured as UTF-16LE by a PowerShell redirect and
  then converted; the decoded text SHA-256 was identical before and after, so the
  conversion changed encoding only.)
- `npm run typecheck` passes with the file in the TypeScript program.

**The file is imported by `src/lib/supabase/server.ts`**, which passes it as the
`Database` generic to `createServerClient`. Table and column names are therefore
typechecked at every call site, so a typo against the live schema is a build
error rather than a runtime surprise. `src/lib/users.ts` reaches the database
through that same client.

### Limits of the generated types

- `uuid` and `text` are both emitted as `string`, so the file does not record
  which ids are `uuid`.
- Constraints are not represented: `users.email` uniqueness, the
  `(roadmap_id, "order")` uniqueness and the `progress_percent` 0-100 CHECK do not
  appear in the types. `progress_percent` is a plain `number`.
- RLS is invisible to the type system, by design.

## Migration status

- Migrations live in **`supabase/migrations/`**, the native Supabase location.
- `supabase/migrations/20260930000000_init_schema_and_rls.sql` is the **single
  initial migration** and the **complete initial database state**: 4 enums,
  8 tables, 11 foreign keys, indexes, CHECK/UNIQUE constraints, grants and 30
  RLS policies.
- `supabase/migrations/20261002000000_learning_goals_relationships_and_priority.sql`
  is the **Phase 1A schema transition migration**: adds `goal_roadmaps`,
  `step_resources`, `notes.step_id`, `learning_goals.priority`, removes
  `roadmaps.goal_id`, and updates RLS policies.
- **Both applied on 2026-10-07.** They were executed through the Supabase SQL
  Editor / `supabase db push` with the session pooler connection, returning
  `Success. No rows returned`. The migration history table now records both
  versions, so a fresh database can be rebuilt from `supabase/migrations/` alone.
- **Do not re-apply these files** and do not convert them into incremental
  migrations. Every later change must be a NEW file in `supabase/migrations/`.
- Prisma never owned the migrations. Its CLI commands and the `prisma/`
  directory no longer exist, so there is no alternative migration path to
  accidentally use.

### Historical note on the superseded migration

The earlier Prisma-generated `prisma/migrations/20260930000000_init/migration.sql`
was **superseded, not extended**. It was never applied to any database, it used
Prisma's camelCase identifiers (`"User"`, `"userId"`), `text` ids and
`timestamp(3)` without time zone, and it contained no RLS. Because nothing had
been applied at the time, an `ALTER`-based follow-up migration would have failed
against an empty schema, so the init file was rewritten in place before anything
reached the database. It has since been deleted along with the rest of the
Prisma infrastructure. This is kept for context only.

## Current data-access state

Prisma is **removed**, and the transition is complete:

- `src/lib/users.ts` writes `public.users` through the **Supabase Data API** using
  the authenticated client from `src/lib/supabase/server.ts`. It is the only
  database-writing module in the application today.
- `src/lib/supabase/database.types.ts` is imported by that client as its
  `Database` generic, so schema changes are caught at compile time.
- `src/lib/db.ts`, `prisma/schema.prisma`, the root `prisma.config.ts`,
  `prisma/migrations/migration_lock.toml` and the generated client under
  `src/generated/` have all been deleted, together with the `@prisma/client`,
  `@prisma/adapter-pg`, `prisma`, `pg` and `@types/pg` packages and every
  `db:*` / `postinstall` Prisma script.
- `DATABASE_URL` has been removed from the zod validation in `src/lib/env.ts`;
  it is not used by any runtime code.
- `tsconfig.json` excludes `src/generated`, so no Prisma artifact is part of the
  TypeScript program.

Because the application now runs as the `authenticated` role only, the earlier
failure mode is gone: there is no connection string in the application that could
bypass RLS or disagree with the snake_case schema.

The database now contains 10 tables, including the Phase 1A join tables
`goal_roadmaps` and `step_resources`, the `learning_goals.priority` column, and
`notes.step_id`. `roadmaps.goal_id` was removed and its associations migrated into
`goal_roadmaps`.

## Row Level Security

RLS is enabled on **all 8 tables** and is the security boundary for the Supabase
Data API. `auth.uid()` identifies the caller; every policy is `TO authenticated`,
and `anon` has no grants on the tables at all.

| Table                 | SELECT | INSERT | UPDATE | DELETE |
| --------------------- | ------ | ------ | ------ | ------ |
| `users`               | own    | `id = auth.uid()` | own | **none (by design)** |
| `learning_goals`      | own    | own    | own    | own    |
| `roadmaps`            | own    | own    | own    | own    |
| `goal_roadmaps`       | both sides owned | both sides owned | **none** | both sides owned |
| `roadmap_steps`       | via roadmap | via roadmap | via old+new roadmap | via roadmap |
| `step_resources`      | both sides owned | both sides owned | **none** | both sides owned |
| `resources`           | own    | own + goal owned   | own + goal owned | own |
| `notes`               | own    | own + resource/step owned | own + resource/step owned | own |
| `summaries`           | own    | own + resource owned   | own + resource owned | own |
| `learning_activities` | own    | own    | **none (by design)** | own |

Rules that matter:

- `roadmap_steps` has no `user_id`; ownership is resolved with `EXISTS` against
  `roadmaps` (`r.id = roadmap_steps.roadmap_id AND r.user_id = auth.uid()`).
- **Cross-user references are blocked.** A plain `user_id = auth.uid()` check is
  not enough on a table with a foreign key to another user's row, so every
  `INSERT`/`UPDATE` policy that carries a nullable reference (`roadmaps.goal_id`,
  `resources.goal_id`, `notes.resource_id`, `summaries.resource_id`) also requires
  an `EXISTS` check that the referenced row belongs to the same user.
- `users` has no `DELETE` policy: accounts are deleted through Supabase Auth.
- `learning_activities` has no `UPDATE` policy: it is an append-only log.
- RLS is enabled but not `FORCE`d, so the table-owner and service-role paths can
  still read the tables. The application uses neither (it queries as
  `authenticated`), so this no longer weakens the boundary for application code.
  `FORCE ROW LEVEL SECURITY` is an open decision.

## Conventions

- `users.id` is a `uuid` from Supabase Auth; every other `id` is `text` holding a
  cuid generated in the application.
- All user-owned rows carry `user_id`; ownership is enforced by RLS in addition
  to application-level filtering.
- Timestamps: `created_at`, `updated_at` (both `timestamptz DEFAULT now()`), plus
  `occurred_at` on `learning_activities`. There is **no `updated_at` trigger yet**.
- Deleting a user cascades. Deleting a `learning_goals` row or a `resources` row
  sets `roadmaps.goal_id`, `resources.goal_id`, `notes.resource_id` and
  `summaries.resource_id` to null so the child rows survive.
- `progress_percent` on `roadmaps` is derived from step statuses; recomputed by the
  server on step updates (Phase 5).
- Validation that stays in the application, not the database, for now:
  `ResourceType` → `url`/`file_path` consistency, and `learning_activities.entity_id`
  polymorphism.

## Deferred indexes and constraints

Intentionally **not** created yet, each because it belongs to a later phase or an
open decision:

- GIN index on `notes.tags` — needed for AI intelligent search (Phase 11).
- Automatic `updated_at` trigger.
- CHECK constraint tying `resources.type` to `url` / `file_path`.
- Any FK or validation on `learning_activities.entity_id`.
- Index on `learning_goals (user_id, priority)` — depends on Phase 4 query patterns.

## Commands

Database changes are applied from `supabase/migrations/` with the Supabase CLI
(`supabase db push`) or the Supabase SQL editor. The initial migration is already
applied; see "Migration status". There are **no ORM scripts** left — the previous
`db:validate`, `db:generate`, `db:migrate`, `db:deploy` and `db:studio` scripts
and the `postinstall` hook were removed together with Prisma, so the only
database workflow is Supabase's.

Regenerating the types (read-only, no database writes):

```bash
npx supabase gen types typescript --project-id <project-ref> --schema public
```

Run it from a shell that writes UTF-8, and compare the decoded text rather than
the byte size if you are unsure the redirect did not re-encode the output.
